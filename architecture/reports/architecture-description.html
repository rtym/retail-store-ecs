System overview — retail-store-ecs

  • Date: 2026-10-09
  • Status: as-built description (reconstructed from the running deployment — see brownfield intake)

What the system does

retail-store-ecs is a deployment of the open-source AWS Containers Retail Sample App (release 1.6.3) on Amazon ECS with AWS Fargate in AWS region eu-central-1. It is a web storefront in which a shopper browses and searches a product catalogue, keeps a shopping cart, checks out and places an order. The upstream project exists to demonstrate container patterns on AWS and states it is for educational use, not production (CON-5).

It is built as five independently deployed microservices, each with its own backing store chosen to exercise a different AWS managed service:

ServiceLanguage (upstream)Backing services (as deployed)
uiJava (Spring Boot)— (calls the other four)
catalogGoAurora MySQL 8.0; OpenSearch 3.3 for search
cartsJava (Spring Boot)DynamoDB (on-demand)
checkoutNode.jsElastiCache Redis 4.0.10; calls orders
ordersJava (Spring Boot)Aurora PostgreSQL 15.10; RabbitMQ 3.13 on Amazon MQ

5. Rationale

  • Service per business capability with private data keeps modules independently deployable and lets each exercise a different managed service — serving BG-1 and MQA-1. Consequence: the shopping journey depends on five services being up at once (AQA-1).
  • Configuration-time binding of providers and endpoints is the main modifiability tactic and the only one available to this deployment, because code changes are out of scope (CON-3).
  • The infrastructure decomposition mirrors the application modules one-to-one, which makes ownership clear but multiplies per-service settings that must be kept consistent (e.g. all five security groups share the same overly broad ingress rule — SQA-2).

2.3 Element interfaces

Interfaces are the upstream HTTP/JSON APIs on port 8080 and the store protocols above. Agreement points visible from the deployment:

  • Scope / interaction style: request-response over HTTP between services; asynchronous publish for order events.
  • Data representation: JSON (application APIs); provider-native protocols to the stores.
  • Error model: health endpoints /health (catalog, checkout) and /actuator/health (ui, carts, orders) are the only error contract the platform uses; retries/timeouts are inside the images and not visible.

2.4 Element behavior

One sequence per architecturally significant use case.

UC-1 / UC-2 — Browse and search the catalogue

Source: diagrams/seq-uc1-browse.puml · UML, rendered with PlantUML · visually verified

The load balancer passes the request to the single ui task, which asks catalog through the Service Connect alias. catalog reads products from Aurora MySQL; when the shopper searches, it queries the OpenSearch products index instead. Every hop is synchronous, so the page fails if any of ui, catalog or the store is unavailable (AQA-1, PQA-1).

UC-3 — Manage shopping cart

Source: diagrams/seq-uc3-cart.puml · UML, rendered with PlantUML · visually verified

carts is the only service that talks to a regional AWS data endpoint. With no DynamoDB gateway endpoint in the VPC, the call leaves through the one NAT Gateway in eu-central-1a — tasks in 1b and 1c cross Availability Zones to reach it, and losing 1a stops all cart writes (AQA-2).

UC-4 / UC-5 — Check out and place order

Source: diagrams/seq-uc4-checkout.puml · UML, rendered with PlantUML · visually verified

Checkout state lives only in the single Redis node; the order is written to Aurora PostgreSQL and an event is published asynchronously to RabbitMQ. Shopper PII crosses four plaintext hops on the way (load balancer, Service Connect, Redis, PostgreSQL) — the core of SQA-1. What orders does when the publish fails after the insert is decided inside the image (CON-3).

UC-6 — Deploy a new service version

Source: diagrams/seq-uc6-deploy.puml · UML, rendered with PlantUML · visually verified

The rolling configuration keeps the old task until the new one is healthy, so a good release causes no downtime. A bad release is never rolled back automatically, and the image pull depends on the public registry and the NAT Gateway (DQA-1).

UC-7 (diagnose) is an operator interaction with CloudWatch and ECS Exec rather than a runtime path between components; it is documented in the observability view.

5. Rationale

  • Synchronous HTTP via Service Connect gives service discovery and load balancing without an internal load balancer and keeps the call graph simple (one interaction pattern) — serving BG-1. The price is a chain of synchronous dependencies: availability of a journey is the product of the availability of every service in it (AQA-1).
  • Database per service isolates failures and schema change to one owner (MQA-1, SQA-2) and lets each service demonstrate a different managed store (BG-1, CON-4).
  • Publish-subscribe for orders decouples future consumers from orders (INQA-1).
  • Single instances everywhere keep cost low (BG-3) at the direct expense of AQA-1 and AQA-2 — analysed in the ATAM.

2.4 Element behavior

Failure of eu-central-1a (the AQA-2 stimulus): the NAT Gateway, Redis, MQ and OpenSearch go down. Tasks in 1b/1c lose all egress (DynamoDB, ECR Public, CloudWatch Logs, Secrets Manager — so even replacement tasks cannot start), checkout and order events stop, search stops. Only browsing from Aurora MySQL in 1c keeps working, if the ui and catalog tasks are not in 1a.

Failure of eu-central-1c: both Aurora writers go down; catalogue, orders and the ui/carts tasks placed there fail until Aurora recovers the instance (single instance, no reader to fail over to).

3. Context diagram

The deployment sits in the shared account 111122223333 next to three other VPCs of unrelated workloads; there is no peering or Transit Gateway between them (CON-1, AC-1). See the account-wide inventory in aws/discovery/architecture-discovery.md.

4. Variability guide

Variation pointHow to exercise it
Number of NAT Gatewaysone per Availability Zone with per-AZ private route tables
Data-store redundancyAurora reader in another AZ; Redis replica + automatic failover; MQ CLUSTER_MULTI_AZ; OpenSearch zone awareness

5. Rationale

The layout — three Availability Zones in the network but one instance of everything else — is the cheapest one that still shows the full topology (BG-3, BG-1). It satisfies CON-2 but fails AQA-1 and AQA-2: the network is ready for multi-AZ, the workload is not. Raising redundancy is mostly configuration, which is why the ATAM rates it a risk rather than a structural flaw.

2.4 Element behavior

Source: diagrams/seq-uc7-diagnose.puml · UML, rendered with PlantUML · visually verified

The trigger is a shopper, not a monitor. The operator works backwards through Container Insights (one day of history), the shared log group and, if needed, a shell opened with ECS Exec — the only diagnostic path the deployment provides for UC-7.

A service starts failing (OQA-1): the container health check fails, ECS replaces the task and logs a service event; the load balancer's 5xx metric rises. Nothing notifies anyone — the first signal is a shopper report. The operator then follows UC-7; evidence older than one day is already gone from Container Insights.

2.3 Element interfaces

The externally reachable interface is HTTP 80 on the load balancer. No WAF, no authentication at the edge; the application's own sign-in is a demonstration feature of the upstream UI.

2.4 Element behavior

Source: diagrams/seq-security-credentials.puml · UML, rendered with PlantUML · visually verified

Credentials never sit in the task definition: the execution role fetches them when a task starts during a deployment (UC-6) and they become environment variables inside the container. From there they are visible to anyone with ECS Exec access to that task, and the database connection that uses them in UC-5 is not required to be encrypted.

Compromised ui task (SQA-2): it can call every other service on 8080 (allowed by design for catalog/carts/checkout/orders) but cannot reach any data store directly — the store security groups stop it. It cannot read the catalog/orders secrets (other execution roles). It can use its task role for CloudWatch Logs only. Lateral movement is therefore limited to the application APIs. Compromised checkout task: can additionally read and modify every cart in DynamoDB (excess dynamodb:*) and read all checkout sessions in the unauthenticated Redis.

3. Context diagram

The trust boundary of interest is the AWS account: it is shared with unrelated workloads and their IAM users (2 without MFA, no password policy) — see the system context and AC-1, AC-3.

5. Rationale

Per-store security groups and per-service secrets show deliberate least-privilege design for the data zone — a non-risk for SQA-2 under the assumption that the store credentials stay scoped. The edge and the application zone were left open, consistent with a demonstration intent (CON-5) but in conflict with BG-4, SQA-1 and SQA-3.

Recovered decisions

#Decision (and where it shows)Rationale, assumptions, alternatives (derived — confirm)Drivers
RD-1Five microservices, one per business capability, each with its own store (module view)Upstream design, deliberately "over-engineered" to show containers with varied dependencies. Alternative: a modular monolith — cheaper and more available, but defeats the demonstration purpose.BG-1, CON-3, MQA-1

Cross-cutting observations

  • The network is multi-AZ, the workload is not (RD-6): the cheapest path to better availability is configuration, not redesign.
  • The data zone is tighter than the application zone (RD-8 vs. the open task security groups): an inconsistency, not a deliberate trade-off.
  • Every decision is constrained by the images being upstream (CON-3): application-level tactics (retries, outbox, idempotency) cannot be changed here.
