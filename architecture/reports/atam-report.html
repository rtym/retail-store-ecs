Step 6 — Analyse architectural approaches (Phase 1 scenarios)

AQA-2 — Loss of Availability Zone eu-central-1a (H, H) ★

  • Attribute / refinement: Reliability / availability, fault tolerance
  • Approaches invoked: AA-10, AA-4, AA-5, AA-2
  • Analysis questions & answers (availability tactics questionnaire):
    • Q: Is there redundancy for every element on the shopper's path? A: Only the load balancer and the network. Services: 1 task each; Redis, MQ, OpenSearch: 1 node in 1a; Aurora: 1 writer each in 1c.
    • Q: Does egress survive an AZ loss? A: No. One NAT Gateway in 1a; the private route table sends all three AZs through it; no VPC endpoints. Without 1a, tasks elsewhere cannot reach DynamoDB, ECR Public, CloudWatch Logs or Secrets Manager — replacement tasks cannot even start (image pull and secret injection fail).
    • Q: Is there failover for state? A: Aurora has no reader to promote; Redis AutomaticFailover: disabled; MQ SINGLE_INSTANCE; OpenSearch ZoneAwareness: false.
    • Q: Would anyone notice? A: No alarms (see OQA-1).

AQA-1 — Single task failure of the storefront (H, M)

  • Attribute / refinement: Reliability / availability
  • Approaches invoked: AA-5, AA-1, AA-2
  • Analysis questions & answers:
    • Q: How is a failed task detected? A: Container health check (curl /actuator/health or /health) and, for ui, the target-group health check. Detection works.
    • Q: Is there a spare to take the load meanwhile? A: No — desiredCount 1 on every service, so the journey is down until the replacement starts, pulls its image and passes health checks.

RQA-1 — Restore after data corruption or deletion (H, M)

  • Attribute / refinement: Reliability / recoverability
  • Approaches invoked: AA-11, AA-4
  • Analysis questions & answers:
    • Q: Can each store be restored to a point in time? A: Aurora yes (7 days). DynamoDB no (point-in-time recovery disabled). Redis no (0 snapshots — acceptable only if checkout sessions are disposable).
    • Q: Is accidental deletion prevented? A: No — deletion protection is off on both Aurora clusters and the DynamoDB table; Terraform destroy would remove them.
    • Q: Are backups copied out of the account/region? A: No AWS Backup plan, no cross-region copy.
    • Q: Has a restore been tested? A: No evidence; RTO unknown.

SQA-2 — Containment of a compromised service (H, M)

  • Attribute / refinement: Security / integrity
  • Approaches invoked: AA-7, AA-8, AA-1
  • Analysis questions & answers (security tactics: limit access, limit exposure, separate entities):
    • Q: Can a compromised task reach another service's store? A: No — each store's security group admits only its owner's task security group. Good.
    • Q: Can it read another service's secrets? A: No — execution roles are scoped to their own secrets.
    • Q: Can anything in the VPC reach every service? A: Yes — all task security groups allow 8080 from 0.0.0.0/0. Today only these tasks live in the VPC, so the exposure is latent.
    • Q: Are task roles least-privilege? A: Mostly; checkout-task holds dynamodb:* on the carts table it never uses, and carts-task holds dynamodb:* rather than item-level actions.
    • Q: Can an operator or attacker with IAM access open a shell in any container? A: Yes — ECS Exec on all five services, and no CloudTrail to record it.

  1. Decide the environment's purpose (ST-1). Demo-only → do the account-wide and cheap items now (RT-3 account baseline, R-7, R-8, R-9, R-4 deletion protection + PITR, log retention) and accept RT-1 explicitly. Production candidate → all four themes, starting with RT-2 and RT-3, then RT-1.
  2. Account baseline first (R-10): it protects every co-tenant too (AC-1, AC-3) and costs little.
  3. Targeted /add iterations, one per theme, recording ADRs: iteration 1 RT-1 (drivers AQA-2, AQA-1, SCQA-1), iteration 2 RT-2 (SQA-1, SQA-2), iteration 3 RT-3/RT-4 (SQA-3, OQA-1, RQA-1, DQA-1).
  4. CBAM to rank RT-1 measures by availability gained per cost (TP-1, TP-2) — cost figures need Cost Explorer data, which is unavailable until the environment-name tag is activated for cost allocation (G-12 in the intake).
  5. Measure before tuning performance: load-test UC-1 and record a baseline for PQA-1/PQA-2.
  6. Locate the Terraform source and state (AC-2); land every change there (CON-6).
  7. Re-run as a Full ATAM with named stakeholders to confirm the drivers and priorities.
